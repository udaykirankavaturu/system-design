# Problem / Context

Choosing a communication protocol for streaming LLM-generated tokens from the server to the client in real-time. The application must support high concurrency (1M QPS target) while maintaining low latency and integrating with the existing HTTP-based architecture.

# Objectives

- Real-time token streaming with minimal latency
- Support high concurrency
- Simplicity and efficiency
- Resilience and automatic reconnection

# Alternatives

- REST (Long Polling)
- WebSockets
- Server-Sent Events (SSE)

# Consequences

| Alternative  | Real-Time | Concurrency | Simplicity | Resilience |
| ------------ | --------- | ----------- | ---------- | ---------- |
| Long Polling | Low       | Low         | High       | Low        |
| WebSockets   | High      | High        | Low        | Medium     |
| SSE          | High      | High        | High       | High       |

# Tradeoffs

- Long Polling - Simple but inefficient, requires repeated requests and introduces latency.
- WebSockets - Excellent for real-time streaming and concurrency, but adds complexity with bi-directional communication that isn't needed for server-to-client-only streaming.
- SSE - Purpose-built for server-to-client streaming, operates over standard HTTP, excellent concurrency support, and provides automatic browser reconnection without custom logic.

# Decision

Use Server-Sent Events (SSE) for streaming LLM tokens to clients. The client sends a prompt via POST request, and the server opens an SSE connection back to stream tokens as they are generated by the LLM. The stream terminates when the LLM sends a final `[DONE]` message.
